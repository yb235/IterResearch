# runrate_nowcast：用三层状态空间模型估计 Anthropic 的 run-rate

**审计数字定水平，先行指标看变化，信源说法补空档。** 三层放在同一个卡尔曼滤波器里：

| 层 | 状态 | 数据 | 作用 |
|---|---|---|---|
| 总量 | log run-rate `l`、增长 `g`、口径差 `b` | S-1 季度 GAAP 收入（锚点）、官方 run-rate、泄露 | 定水平 |
| 分部 | 消费 / 订阅（分割，份额和为 1）；云渠道、Claude Code（叠加层） | S-1 H1 拆分（消费 80% / 订阅 20%，云渠道 48%）、Claude Code 官方数字 | 拆结构 |
| 先行指标 | 每个指标一个**会漂移的截距** `a_i` | npm / PyPI SDK 下载、Ramp 企业 token 支出（每周） | 看变化 |

先行指标的观测方程是 `log(指标) = a_i + β_i·log(分部收入) + 噪声`，其中 `a_i` 是随机游走。指标与收入的关系不假定固定，而是每天都允许变化，审计数字一到就重新校准。

```bash
pip install -r runrate_nowcast/requirements.txt
python -m runrate_nowcast update-data                        # 抓取 npm / PyPI / Ramp
python -m runrate_nowcast nowcast --asof 2026-11-10 --plot   # 报告和两张图写入 reports/
python -m runrate_nowcast layers                             # 逐层回测（约 25 秒）
python -m runrate_nowcast audit                              # 手定选项的敏感性审计（约 8 分钟）
python -m runrate_nowcast layers --refit                     # 严格样本外逐层回测（约 20 分钟）
python -m pytest runrate_nowcast/tests -q                    # 约 260 个测试，约 4 分钟
```

## 最新（2026-11-13 下午）：单价能解释高估吗？按模型的单价指数（价格研究）

**问题**：收入 = 用量 × 每 token 单价。现有指标（npm / PyPI SDK 下载量）只量用量，而 Anthropic 2026 年多次降价（Sonnet 6/30 −33%，Opus 9/22 −20%，Haiku 10/7 −90%，5.5 系列缓存读取减半）。指标模型对最近三个官方目标（Q3 收入、9/30 的 $71B、10/31 的 $81B）全部高估。假设：每 token 单价下降解释了高估。这里检验它，而不是假定它。

**规则**：S-1、S-1/A 等申报数字只用来打分，从不作输入（`filing = 1/2`）；每个时点所有参数用当时的数据重估；交叉位置按时点估计。分析选择在跑 C、D 之前写进 `price_study.py` 并推送（提交 `bfb119d`；当时 A、B 已经跑过）。

### 结论

1. **在这组数据上，“单价下降解释了高估”这个假设基本不成立。** 价格调整后的指标（C）和原始指标（B）在两种时点、两种规则下都打平，差值在 ±0.01 以内，90% 区间都包含 0。
2. **原因是实测的模型组合：Q3 的单价不降反升。** 7–9 月公开 commit 里 Fable（两倍于 Opus 的价格）一度占 20%–40%，按组合算的单价比 6 月高 10%–40%。所以价格调整让 Q3 收入和 9/30 的预测更差（期末当天：Q3 从 +40% 变为 +55%，9/30 从 +79% 变为 +96%），只让 10/31 变好（+115% 变为 +101%）。直接分解也是这样：Q3 的缺口（0.30–0.57）单价解释不了，10 月的缺口（约 0.13）单价基本能解释。
3. **当时的证据只是轻微偏向 γ = 1**（最后几个时点约 0.55–0.64），而且偏向并没有带来更好的预测。按联合似然，证据则几乎全在 γ = 0。
4. **缓存口径（C′）有小而稳定的改进**，四个比较里有三个 90% 区间不含 0，约 −0.015。但它的权重比例是 10–11 月事后测的，又是好几个敏感性分析中的一个，只能算线索，不能算结论。
5. **GitHub commit 数直接当指标会显著变差**（期末当天 +0.21，区间 [+0.07, +0.35]）。commit 总数 9 月到 11 月涨了约 4 倍，远快于收入。它只适合用来算组合。
6. **高估的大头不在指标层，而在说法层。** 默认规则下，没有任何指标的 A 也把 9/30 高估 64%、10/31 高估 71%；改用 N 规则后，A 降到 0.165，是这里最好的。价格调整最多只能修正指标在 A 之上额外加的那一部分（期末当天 B 比 A 多出 2–44 个百分点），而这一部分本身在统计上也不显著。
7. **这个价格指数有结构性缺陷。** commit 反映的是 Claude Code 用户（很多是包月订阅），他们选哪个模型并不改变收入。OpenRouter（按 token 计费）每周前 9 名里从未出现 Fable，和 commit 里 40% 的 Fable 对不上。真正需要的是按量计费部分的模型组合，现有公开数据里没有。Ramp 的 10 月数据（花费 +8.9%、用量 +37.1%，即单价约 −20%）和 10 月的分解方向一致，但 Ramp 的历史太短，进不了回测。
8. **样本很小。** 13–15 个目标，其中真正检验下半年的只有 Q3、9/30、10/31 三个，时间上重叠，接近一次事件。上面所有“显著”都应打折看。

## 最新（2026-11-12 深夜）：ML 结果为什么奇怪，修了之后怎样（子任务 L、M）

**诊断**（`reports/zoo_diagnostics_2026-11-12.md`）：

- 把所有信号放进一个模型，误差从 0.13 涨到 0.76。问题出在 GitHub commit 数和 OpenCode 下载量：它们衡量的是产品普及，一年涨了几百到几千倍。用来定水平的收入锚点只有十几个，模型分不清哪个信号可信。最极端的一个例子是，对 2025 年 10 月 run-rate 的预测高了 95 倍。
- 各信号单独建模再组合也被拖累了。早期目标还没有“过去表现”可以用来加权，所以等于等权平均，坏信号的大误差就进来了。
- 数据多不等于好。普及型的数据要先变换才能用，例如换成相对竞争对手的份额，或者只看增长率。直接拿水平值当指标不行。

**ML 的结果：**

- ridge 有收缩，所以不会像状态空间那样被坏信号拉崩，但也没有超过只用 OpenRouter 的简单模型。
- 加了全部信号的 ML，在公布前一天的时点上从 0.187 降到 0.173，在期末当天的时点上从 0.234 升到 0.250。两个变化的 90% 区间都包含 0，也就是没有显著差别。
- 瓶颈和之前一样，是标签。ML 学的是收入路径的变化，而这条路径是在信源说法之间插值出来的。Q3 几乎没有说法，所以 ML 在最需要的那段时间学不到东西。

1. **不用 S-1，2026 年下半年所有模型都大幅高估**：9/30 高 40%–80%，10/31 高 65%–120%。原因是 5 月以后公开的说法很少，模型延续了上半年每月 20%–50% 的增长，而实际 Q3 几乎停滞（7 月底约 660 亿，9/30 是 710 亿）。

   - 当时的似然不会选它（见上表“事后选择”）；
   - 它只修正了一部分高估。
   “收入 = 用量 × 单价”这个结构，是在跑回测之前就写进了建模计划（commit `6277559`），不是看结果才加的。
4. **GitHub commit 数直接当指标会更差**：10 月 commit 数翻了一倍多，收入只涨 14%。它的用处在于算模型组合和单价。
5. **贝叶斯版区间最诚实**（80% 区间覆盖约 79%），但点预测同样高估。
6. **现有的实时数据看不出 Q3 的增长放缓。** 要预测这类拐点，需要离钱更近的数据，例如刷卡面板、云厂商财报，或者更多公司自己的说法。

## 0. 哪些是拍脑袋定的、哪些真正影响结论、哪些说过头了

### 0.1 方法

把代码和数据里所有手定的数字、规则和设定列出来（约 25 项），逐项换成合理的替代值（一般取一半和两倍，或换成另一种规则），其他保持不变，看四个结果怎么变：10/31 run-rate、Q4 收入、回测误差、80% 覆盖率。“重要”的标准是：移动 10/31 超过 80% 半宽的一半（约 3.6），或移动 Q4 超过 1.9，或移动回测误差超过 0.01。完整结果见 [`reports/audit_2026-11-10.md`](reports/audit_2026-11-10.md)，命令是 `python -m runrate_nowcast audit`。

### 0.2 结果：大部分手定项不影响结论

| 手定项 | 最大影响（10/31，$B） | 结论 |
|---|---|---|
| official / leak / GAAP 信源噪声 | ≤1.4 | 不重要 |
| 分部层所有常数（份额先验、漂移、和为 1 约束） | ≤0.2 | 不重要（分部层不影响总量） |

### 0.3 已经从“人定”改成“规则或数据定”

- **日期**：每条说法记录原文措辞允许的时间窗口，例如“本月早些时候突破 $47B”对应 5/1–5/28。日期取窗口中点，不确定性取窗口宽度 / √12（窗口内均匀分布）。措辞依据写在 `date_rule` 列。
- **分部份额的近似误差**：由份额的漂移速度推导，σ × √(天数 / 12)，不再手填 0.03。参考日期取按 GAAP 季度收入加权的中心（4 月 20 日），因为期间份额本身就是收入加权平均。
- **断点**：用规则检测。条件是同一来源的竞品序列（例如 PyPI 的 `openai` 包）同一天同方向变动超过 25%，并且 28 天后仍未恢复，同时排除 12/20–1/6 假期。规则只检出 PyPI 8/25 一个断点（anthropic −41.6%、openai −41.9%），和之前人工判断一致，测试会检查目录与规则是否一致。
- **假期**：指标的周均值不计 12/20–1/6。
- **数据定不下来的设定，做加权平均而不是挑一个**：领先/滞后（5 个值）× 弹性（3 个值）× 漂移（4 个值）× 第三方噪声（3 个值）× 定义滞后（2 个值），共 360 个组合，每个组合的权重 = 先验 × 在线滤波似然（`robust.py`）。

## 0d. 完整贝叶斯升级（`bayes.py`，命令 `python -m runrate_nowcast bayes` / `bayes-backtest`）

依据第 0 节和 [LITERATURE.md](LITERATURE.md) 第 1 节（混合频率贝叶斯状态空间模型），做了三处改动：

1. **共享因子**：npm 和 PyPI 两个 SDK 下载量共用一个“开发者活动相对收入”的漂移，另外各有独立的漂移。原来两个指标同时偏离收入时，会被当成两份独立证据。
2. **分季度的增长波动率**：增长冲击的方差按季度乘以 exp(v_q)，各季度的 v_q ~ N(0, 0.7²)。这是随机波动率的分段近似。
3. **参数后验**：约 20 个参数都有明确的先验。先求 MAP，再用 Laplace 近似得到后验，预测时对 24–32 个后验抽样做混合，区间因此包含参数本身的不确定性。离散设定（指标滞后、定义滞后）按 Laplace 证据加权。

**严格样本外回测**：每个目标只用它公布前一天的数据，从目录先验出发重新拟合全部参数。结果保存在 [`reports/bayes_backtest_2026-11-10.csv`](reports/bayes_backtest_2026-11-10.csv)。

| 版本 | log 误差 | 80% 覆盖率 | 50% 覆盖率 | z 的标准差（理想值 1） |
|---|---|---|---|---|
| 原版（点估计，各指标独立） | 0.115 | 69% | 38% | 1.67 |
| 新结构，参数仍取点估计 | 0.120 | 77% | 31% | 1.30 |
| **新结构 + 参数后验** | **0.115** | **92%** | **46%** | **0.85** |

- **区间校准问题基本解决**：z 的标准差从 1.67 降到 0.85，50% 覆盖率接近名义值，80% 覆盖率略偏保守。主要来自参数后验，共享因子和波动率参数的贡献较小。
- **准确度没有变**（0.115）。这一步改的是“知道自己有多不确定”，不是“更准”。
- **Q3 2026 仍高估约 21%**（log 误差 −0.206，z = −2.0）。共享因子在有独立支出数据时能把这类高估减少约 17%（见测试 `test_shared_factor_reduces_double_counting`），但当实时证据只有下载量时，“两个下载量指标一起涨”最合理的解释仍然是收入涨了。真正的解决办法是离钱更近的数据（第 7 节）。

**当时的估计**（加入 S-1/A $81B 之前；10/31 的实际值是 81，落在这个区间外。更新后的估计见最上面一节）：

| 量 | 后验中位数 / 均值 | 80% 区间 |
|---|---|---|
| 10/31 官方口径 run-rate | 95.3 | [84.9, 107.3] |
| 11/10 官方口径 run-rate | 101.9 | [89.4, 117.2] |
| Q4 2026 收入 | 28.4 | [23.7, 33.4] |

各结构按 Laplace 证据的权重：
- run-rate 定义滞后：7 天占 80%，14 天占 20%。
- 指标领先/滞后：+7 天（指标落后收入一周）占 53%，0 天占 34%，−7 天占 13%。

这个估计已作为第三条登记进 `forecasts/registry.jsonl`。Q4 公布后会同时对账三个版本：只用信源说法 $21.4B、三层模型 $28.2B、贝叶斯升级版 $28.4B。三层模型和贝叶斯升级版都依赖先行指标，而 Q3 的教训正是这些指标可能高估。。

## 0c. 用 ML 行不行：插值标签训练，真实锚点验证

做法（`ml.py`，命令 `python -m runrate_nowcast ml`）：
- **训练标签**：在真实数据点之间估计每周的标签，两种方式：log 线性插值，或只用信源说法的状态空间平滑路径。
- **模型学什么**：学“先行指标的变化 → 收入的变化”，学增长而不是水平，因为树模型不能外推到没见过的水平。模型有三个：只延续趋势（不用指标）、ridge（线性）、gbm（梯度提升树）。正则化强度和树的参数用按时间顺序的交叉验证选，不是手定的。
- **验证**：只在之前那 13 个真实目标上做。每个目标只用它公布之前的锚点和指标数据，有专门的测试防止用到未来数据。

| 方法 | 平均 log 误差（12 个共同目标） | ML 实际起作用的 5 个目标 |
|---|---|---|
| 状态空间，只用信源说法 | 0.130 | 0.234 |
| 状态空间 + 先行指标 | 0.110 | 0.159 |
| ML ridge（平滑路径标签） | **0.107** | 0.168 |
| ML ridge（线性插值标签） | 0.111 | 0.171 |
| ML gbm（平滑 / 插值标签） | 0.119 / 0.152 | 0.197 / 0.270 |
| 只延续趋势（平滑 / 插值标签） | 0.138 / 0.127 | 0.244 / 0.209 |
| 状态空间 + ridge 等权平均 | **0.087** | |

- **线性 ML 和状态空间模型打平**：配对差 −0.003，90% 区间 [−0.04, +0.04]。
- **非线性 ML 更差**：插值标签的 gbm 显著更差 [+0.002, +0.089]。插值标签并不增加独立信息，能用来验证的目标太少。
- **两者等权平均最好（0.087）**，两者误差的相关系数是 0.71。不过这是在同一批目标上事后看出来的，只能算有希望。
- **ridge 学到的关系**：收入变化主要跟 Anthropic SDK 相对 OpenAI SDK 的 npm 份额走（弹性 0.27–0.39），对下载量本身的弹性只有约 0.17，而状态空间模型里约为 1。也就是说，ML 从数据里学到了“下载量的波动会夸大收入的波动”，这和 Q3 那次高估是一致的。
- **ML 对现在的估计更保守**：11/10 官方口径 run-rate，插值标签给 $81B，平滑标签给 $88B；状态空间是 $103B。

完整结果见 [`reports/ml_2026-11-10.md`](reports/ml_2026-11-10.md) 和 [`reports/ml_vs_statespace_2026-11-10.csv`](reports/ml_vs_statespace_2026-11-10.csv)。

**结论：瓶颈是独立标签的数量，不是算法。** 等有了跨公司的面板数据（标签从十几个变成几百个），用同一套评估流程就能重新评估 gbm 等非线性模型。

## 0b. （上一版）“用历史数据预测未来”是不是假的？

> 注意：本节的回测数字是用全样本拟合参数得到的，偏乐观。严格样本外的结果见第 0.4 节。

| 变体（同一组 13 个目标，只用公布前一天的信息） | 80% 覆盖率 | log 误差 |
|---|---|---|
| A 只用总量信源说法（v1） | 77% | 0.138 |
| B + 分部说法 | 92% | 0.137 |
| **C + 先行指标（默认）** | **85%** | **0.081（−41%）** |
| D + 公司 / 第三方预测 | 77% | 0.086 |
| C 但先行指标不标定（用目录里的先验参数） | 31% | 0.228 |
| 朴素外推（最近一个官方数字） | — | 0.297 |

1. **你说得对的一半：单靠收入趋势外推，在拐点处会失效。** v1 在 Q3 数据出来之前预测 10 月 run-rate 为 $116–144B，因为它把上半年约 30%/月的增速一直外推。先行指标在两次披露之间提供了真实的“当期”信息，回测误差下降 41%。改善主要出现在官方数字稀疏的时段：2025 年 10 月从 0.46 降到 0.15，2026 年 2 月从 0.39 降到 0.09。
2. **需要补充的一半：另类数据同样要用历史来标定。** 不标定的 SDK 下载放进模型比完全不用还差（0.228）。原因是下载量每周的变化约为 ±10%，而且变化本身没有自相关，也就是说它有自己的随机游走，不是“收入加白噪声”。历史数据在这里的用途不是外推收入，而是估计每个指标的弹性 β 和漂移速度。拟合出的结果是：npm SDK 的 β≈1.0，漂移 0.033/√天；PyPI 的 β≈1.0，漂移 0.014/√天。参数取整数附近的值（β=0.85，漂移 0.01–0.03）时误差为 0.073–0.075，所以收益不依赖精确拟合值。
3. **公司和第三方的预测：默认不放进滤波器，单独记分。** 放进去后误差反而略升（0.081 → 0.086）。
   - 公司 2025 年 10 月对“2026 年底 run-rate”的内部目标是 $20–26B，模型现在估计约 $134B，只有实际的 1/5。
   - 同一时间对“2025 年底 $9B”的短期目标则很准（0.96）。
   - FT 8 月的投资者预期 $100–120B，与模型的差距是 0.82。

   预测类说法的价值取决于预测期长短和来源的历史命中率，所以先攒记录（报告里的 “Forecast claims” 表），等证明可靠后再按预测期给权重。
4. **分部层不提高总量精度（A→B 基本不变），但 80% 覆盖率从 77% 提高到 92%，并给出结构信息。** 只有消费 / 订阅这一组拆分经过审计，云渠道和 Claude Code 是根据披露和估算推出来的，区间较宽。

3. **Bloomberg 的“7 月底 >$65B”与 Q3 GAAP 有些冲突**，为真的概率在 29% 到 53% 之间，取决于口径差 b 随时间漂移得多快（见第 5 节的敏感性分析）。要让 Q3 收入只有 $16.96B，同时 7 月中旬瞬时值就已 ≥ $65B，Q3 内的增长就只能很慢。
4. **新发现：官方 run-rate 相对 GAAP 的偏差在漂移。** 把每个官方数字与“只用 GAAP 季度收入推出的路径”比较：

   | 官方说法 | GAAP 推算值 | 偏差 |
   |---|---|---|
   | $9B（2025 年底） | $9.8B | −8% |
   | $14B（2026 年 2 月） | $15.2B | −8% |
   | $19B（2026 年 3 月） | $18.5B | +3% |
   | $30B（2026 年 4 月） | $27.2B | +10% |
   | $47B（2026 年 5 月） | $40.6B | **+15%** |

   2026 年上半年，官方 run-rate 从略低于 GAAP 变成明显高于 GAAP。可能的原因包括：run-rate 与 GAAP 对折扣、赠送额度的处理不同（S-1 显示云渠道收入在 GAAP 里也按总额确认，所以不是总额/净额差异）；×13 的年化方式放大了高峰期；或者“突破 $X”这类表述本身就挑在高点发布。这正是要用审计数字校准其他信源的原因。

## 3. 模型

### 状态（按日步进）

| 状态 | 含义 |
|---|---|
| `l` | log 瞬时年化收入（GAAP 口径） |
| `g` | 月度 log 增长率。Local linear trend：`l' = l + g/30.44`，可选阻尼：`g' = g + κ(ḡ − g)/30.44` |
| `b` | 报告 run-rate 相对 GAAP 的 log 口径差（随机游走） |
| `A_k` | 期间 k 的累计收入。每个被观测或被查询的季度、年、月各有一个累加器，每天加上 `exp(l)/365`，期初清零 |
| `s_k` | 分部 k 的 log 份额（随机游走）。消费和订阅是分割，每周施加一次软约束 Σexp(s_k)=1，非线性部分按统计线性化处理；云渠道和 Claude Code 是叠加层，不受约束 |
| `a_i` | 先行指标 i 的 log 截距（随机游走，漂移速度单独估计）。目录里登记的断点日期给截距加一次大方差，用来吸收统计口径变化 |

季度收入因此是状态的一部分，“季度收入等于月度路径的积分”这条约束是精确成立的，不需要事后对账。

### 观测方程（都是状态的线性函数）

- run-rate 说法：`log(y) = l(t − lag) + b + tier_bias + ε`，`ε ~ N(0, σ_tier² + (g·date_sd)²)`
- 收入说法：`y = A_k(期末) + ε`
- 分部份额（例如 H1 订阅占 19.6%）：`log(y) = s_k + ε`，期间平均份额近似为收入加权中点的份额，额外加 0.03 的噪声
- 分部 run-rate（例如 Claude Code $1B）：`log(y) = l + s_k + b + ε`
- 先行指标（每周均值）：`log(I) = a_i + β_i·(l + s_seg) + ε`
- 预测类说法（`is_forecast=1`）：噪声按预测期加大 0.08/月；默认不进滤波器
- “超过 $X” / “不超过 $X”：截断观测。对观测的线性组合做截断正态的矩匹配（assumed-density filtering）。`tests/` 里用拒绝采样核对过，误差在千分之几以内。

### 非线性

`A_k` 是 `exp(l)` 的累加，所以是非线性的。预测步用了精确矩：`E[e^u] = exp(m + v/2)`，再由 Stein 引理得到 `Cov(x, e^u) = P c E[e^u]`，没有做线性化。有一个问题：当某个季度数字离预测很远时（例如 Q3 预测约 $27B、实际 $16.96B），单次高斯更新会让日度路径和累加器对不上，初版模型就算出了 9 月收入低于 8 月。所以平滑用的是 **iterated posterior linearization smoother**：每一轮围绕上一轮的平滑后验做统计线性化，再跑一遍卡尔曼滤波和 RTS 平滑，通常 5–6 轮收敛。

### 参数（[`params.json`](params.json)，由 `fit --write` 和 `fit-indicators --write` 生成）

先行指标参数（MAP，先验来自 [`data/indicator_catalog.csv`](data/indicator_catalog.csv)）：

| 指标 | β（弹性） | 截距漂移 /√天 | 周观测噪声 |
|---|---|---|---|
| npm `@anthropic-ai/sdk` | 1.00 | 0.033 | 0.031 |
| PyPI `anthropic` | 1.00 | 0.014 | 0.019 |
| Ramp token 支出 | 0.83 | 0.005（先验） | 0.089 |

总量层参数（v1 的数字；加入指标后重估：σ_g 0.017、κ 0.15，变化不大）：

| 参数 | 值 | 怎么来的 |
|---|---|---|
| σ_g（增长冲击） | 0.017 /√天 | MAP 估计，log sd 0.26，识别得较好 |
| κ（增长回归速度） | 0.12 /月（半衰期约 6 个月） | MAP 估计，log sd 0.62 |
| σ_l（水平冲击） | 0.0038 /√天 | 基本由先验决定，数据识别不了 |
| σ_b（口径差漂移） | 0.0019 /√天 | 基本由先验决定，见第 5 节的敏感性分析 |
| 信源噪声 | official 0.04，leak_tier1 0.08，leak_single / third_party 0.15 | 默认值，见下 |

目标函数是在线滤波器的 prediction-error likelihood（真正的一步向前预测误差），加上弱先验。只有约 22 条观测，所以每个参数的识别程度都列了出来。

**信源打分**（`calibrate`）：先只用 GAAP 收入拟合一条“审计真值”路径，再计算每个信源的历史说法相对这条路径的残差，用带收缩先验的 MLE 估计每个 tier 的偏差和噪声。目前只有 official 有 6 个点值，拟合出的 sd 为 0.040，与默认值一致。其他 tier 只有 1–2 个点，不足 3 个点就不覆盖默认值，以免用一两个数据点给信源定权重。这一步和你 bestanalysts 的信源打分加回测是同一套逻辑：样本攒够之后，同一段代码就能自动给出各信源的噪声。

## 4. 怎么保证正确

> 本节是 v1（只用信源说法）的回测记录。三层模型的逐层回测见第 0 节，命令是 `python -m runrate_nowcast layers`。

**回测**（`backtest`）：对每个 GAAP 季度和每个官方 run-rate，只用它公布前一天的信息（同源报道一并剔除），预测它的数值。

| | 80% 覆盖率 | 50% 覆盖率 | z 的标准差 | log MAE | 朴素基准 log MAE |
|---|---|---|---|---|---|
| 全样本超参数（n=13） | 85% | 23% | 1.00 | **0.143** | 0.297 |
| 每个时点重新拟合超参数（`--refit`，严格实时） | 77% | 31% | 1.25 | 0.141 | 0.297 |

朴素基准的做法：run-rate 沿用最近一个点值；季度收入把各 run-rate 点值按 log 线性插值后对时间积分。模型误差约为基准的一半，80% 区间基本校准。严格实时版本的 z 的标准差为 1.25，说明区间略偏窄。n=13 太小，50% 覆盖率的波动很大。另外 z 的均值为 +0.3：实际公布的数字往往高于模型的事前预测，与第 1 节发现的官方口径上漂是同一个方向。

**回测暴露的问题**：Q3 数据公布前（10/30），模型对 10 月 run-rate 的预测是 $116B [68, 200]，加阻尼前是 $144B。原因是 local linear trend 会把 Q1–Q2 约 30%/月的增长一路外推。加入增长回归（κ）后，似然和回测都有改善（log MAE 从 0.180 降到 0.143），所以保留了这一项。它仍然说明：**新季度数字出来之前，模型对增速放缓的反应偏慢。** 先行指标层（第 6 节）就是为了补这一块。

**合成数据测试**（`tests/`）：已知真实路径，增速从 30%/月降到 8%/月，口径差 b = 0.06。模型能复现每个季度的收入；80% 区间在 88%–100% 的天数里覆盖真值，略偏保守；b 的估计在真值附近。

**事前登记**（`register` / `score`）：把预测加上时间戳追加到 [`forecasts/registry.jsonl`](forecasts/registry.jsonl)，并记录 git commit 和数据文件的 sha256，然后立即提交。git 历史就是时间戳的凭据。记录内容是未来 120 天的 run-rate 预测扇面，加上未披露期间的收入预测，所以无论下一个数字哪天公布、落在哪个日期，都能对账。第一条记录已经登记，包括 Q4 2026 收入 $21.4B [16.7, 26.6]。

## 5. 敏感性：口径差 b 漂移多快

数据几乎识别不了 σ_b：似然轻微偏向慢漂移，回测轻微偏向快漂移。默认用事先定好的 MAP 值，不按回测结果去调。

| σ_b | b（5 月 → 11 月） | 9/30 官方口径 | 10/31 官方口径 | Q4 收入 | P(WSJ >80) | P(BBG >65) | 回测 MAE |
|---|---|---|---|---|---|---|---|
| 0.0019（MAP，默认） | +0.011 → +0.014 | 73.2 [68.7, 77.8] | 78.7 [70.0, 88.5] | 21.4 [16.7, 26.6] | 33% | 29% | 0.143 |
| 0.005 | +0.042 → +0.053 | 75.4 [69.4, 81.8] | 79.6 [70.6, 89.7] | 20.5 [15.7, 25.8] | 35% | 41% | 0.139 |
| 0.010 | +0.084 → +0.086 | 77.3 [69.1, 86.5] | 80.3 [70.9, 91.0] | 19.9 [14.7, 25.6] | 36% | 53% | 0.132 |

10 月底的估计和 WSJ 判断都很稳健，受影响较大的是 Bloomberg $65B 的可信度和 Q4 收入。

## 6. 每天怎么更新

```bash
# 0. 先行指标：每天抓 npm / PyPI，每周抓 Ramp 快照（PyPI 只保留 180 天，Ramp 只显示两期，必须持续抓才有历史）
python -m runrate_nowcast update-data
# 1. 抓取和抽取：把新说法追加到 data/observations.csv（日期、数值、上界/下界/点值、口径、tier、origin_id、URL、segment、is_forecast）。
#    多篇文章转引同一条报道时用同一个 origin_id，必须追到原始出处。预测性表述设 is_forecast=1（单独记分，不进滤波器）。
# 2. 报警：新说法与“公布前一天的模型”比较，|z|>2 或下界成立概率 <2.3% 时报警
python -m runrate_nowcast alerts --since 2026-11-03
# 3. 更新 nowcast
python -m runrate_nowcast nowcast --plot
# 4. 在下一次披露前（例如 Q4 财报、IPO 定价文件）登记预测并提交
python -m runrate_nowcast register --note "pre-Q4 10-K" && git add runrate_nowcast/forecasts && git commit -m "register forecast"
# 5. 披露之后对账；每月重新估计参数
python -m runrate_nowcast score
python -m runrate_nowcast fit --write && python -m runrate_nowcast fit-indicators --write && python -m runrate_nowcast calibrate
# 6. 新加一个指标：在 indicator_catalog.csv 里先设 role=monitor，跑 layers 看回测是否改善，再改成 model
```

含先行指标后，单次滤波加平滑约 2 秒，完整报告约 10 秒，逐层回测约 25 秒，指标参数拟合约 20 秒。

## 7. 下一步（按对精度的价值排序）

严格样本外回测说明，现在的瓶颈不是模型结构，而是**标定先行指标所需的历史太短**。早期目标只能靠目录里的先验参数，而这些先验是我定的，审计也证明它们不好。所以优先做能让先验变成“由数据定”的事：

1. **用其他公司的数据给指标先验**（跨公司的经验贝叶斯）。同一个问题在 OpenAI 身上也存在：`openai` SDK 下载量与 OpenAI 公开收入之间的弹性和漂移，可以作为 Anthropic 指标的先验，取代我手定的 β=0.75、漂移 0.003。数据（npm、PyPI 的 `openai` 包）已经在 `indicators.csv` 里，需要补的是 OpenAI 的收入和 run-rate 说法。
2. **每周自动抓取**：npm、PyPI、Ramp、OpenRouter。历史越长，指标参数越能由数据决定；PyPI 只保留 180 天，Ramp 和 OpenRouter 只显示两期，不抓就丢了。
3. **离钱更近的数据**：Ramp（用 web.archive.org 回填，需要放行该主机）、付费信用卡支出面板、云厂商财报。
4. **SEC 原文**：第 2 号修订里的 10/31 数字已用全文检索（efts.sec.gov，不需要邮箱）逐字核对。下载完整原文仍然要求 User-Agent 带联系邮箱，需要你提供一个。拿到后可以核对所有二手数字，包括季度收入。
5. **区间校准**：严格样本外 z 标准差约 1.5–1.7，报告里给出按此放宽的区间。目标样本多了以后，再按预测期分别校准。
6. **分部趋势项**：Claude Code 份额的上升快于随机游走的假设。
7. **抓取和抽取流水线**：可以接到本仓库的 IterResearch agent 上。
